## 0. تحديد نوع اللعبة والمحرك

| البند | التحديد |
|---|---|
| **التقنية** | Three.js r0.160.0 عبر ES Modules + import map، بلا خطوة بناء (no build step) |
| **البنية** | ملف واحد `index.html` يعمل كـ PWA أوفلاين، رسومات إجرائية بالكامل (canvas-generated) |
| **نوع اللعبة** | Endless-runner / Arcade driving بمنظور مطاردة (chase camera) على مسار ثلاثي الأبعاد |
| **نمط اللعب** | **فردي أوفلاين بالكامل** — لا خادم، لا حساب، لا لوحة نتائج مركزية |
| **الأوضاع** | قصة (٦ مراحل) · سباق وقت · لا نهائي · تحدٍّ يومي ببذرة مشتركة |

**تعديل المعايير بناءً على النوع** (وهذا مُصرَّح به في كل قسم أدناه):

- اللعبة **أوفلاين فردية** → ملف الحفظ في `localStorage` بنص صريح **ليس ثغرة**، هو خيار
  تصميمي سليم. لن أُحاسب المشروع عليه.
- لا يوجد خادم ولا لوحة نتائج → التحقق من النتائج على الخادم غير قابل للتطبيق أصلاً.
- **لكن**: وضع «التحدي اليومي» يَعِد صراحةً بـ«بذرة يومية ثابتة للجميع» ويوفّر زر مشاركة
  للنتيجة. هذا الوعد يحوّل *نزاهة البذرة* إلى معيار عادل للمحاسبة — وهو المحور الذي
  انكسر فعلاً (انظر 🔴 A1).
- لعبة قيادة بفيزياء تضاريس → الفيزياء و delta-time و object pooling **معايير أساسية**
  هنا، لا كماليات.

## 1. المراجعة التقنية والهندسية (وزن 40%) — **8.0/10**

### أ) حلقة اللعبة والأداء — 8.5/10

**ما نُفّذ باحترافية (وأقولها بصدق، مو مجاملة):**

`delta-time` مطبّق بشكل **صحيح رياضياً** في كل مكان تقريباً، لا بالطريقة الساذجة
`x += speed * dt` فقط، بل بالصيغة الأسّية الصحيحة للتنعيم (exponential smoothing):

```js
const steerBlend = 1 - Math.pow(CONFIG.vehicle.steeringDamping, delta * 60);
const follow    = 1 - Math.pow(1 - CONFIG.vehicle.terrainFollowSpeed, delta * 60);
state.throttleApplied += (state.throttle - state.throttleApplied) * (1 - Math.exp(-3 * delta));
```

وحتى عتبة القفز عن الحواف حُوِّلت من فرق ارتفاع لكل إطار إلى **معدّل هبوط بالثانية**:

```js
const dropRate = heightDiff / Math.max(delta, 1e-4);
if (dropRate < CONFIG.vehicle.launchDropRate) { ... }
```

هذي بالضبط الأخطاء القاتلة اللي أدوّر عليها عادةً في ألعاب الويب، ومعالَجة هنا بوعي.

`getTerrainSlope()` مشتقة **تحليلية** لـ `getTerrainHeight()` (بقاعدة الضرب للـ goal-flatten)،
تُستخدم لكتابة الـ normals مباشرة بدل `computeVertexNormals()` — وهذا يزيل الاختناق
(stutter) عند إعادة تدوير قطع التضاريس في الوضع اللانهائي. والأهم: **مغطّاة باختبار**
يقارنها بالمشتقة العددية على شبكة كثيفة.

Object Pooling موجود فعلاً (`obstaclePool` / `fuelCanPool` / `powerupPool` / `debris`)،
وكشف التصادم `O(n)` على قوائم قصيرة (~20–60 كائن) وهو مناسب تماماً لمسار خطي — التقسيم
المكاني (spatial partitioning) هنا سيكون هندسة زائدة.

**الملاحظات:**

**🟠 P1 — `playCrash()` يخصّص مخزن ضجيج جديد عند كل اصطدام**

`index.html` — في `AudioSystem.playCrash()`:

```js
const bufferSize = this.ctx.sampleRate * 0.4;
const buffer = this.ctx.createBuffer(1, bufferSize, this.ctx.sampleRate);
const data = buffer.getChannelData(0);
for (let i = 0; i < bufferSize; i++) {
    const decay = Math.pow(1 - (i / bufferSize), 2);
    data[i] = (Math.random() * 2 - 1) * decay;
}
```

عند 48kHz هذا **19,200 استدعاء `Math.random()` + تخصيص `Float32Array` بـ 76KB** على
الخيط الرئيسي، في نفس اللحظة اللي فيها الكاميرا تهتز وتنفجر الشظايا و`hitStop` شغّال.
الاصطدام هو أكثر لحظة حسّاسة للاختناق في اللعبة، والصوت نفسه **متطابق في كل مرة**.

البديل: ولّد المخزن مرة واحدة في `setupWind()`-style عند `init()` واحتفظ به، ثم لكل
اصطدام أنشئ `BufferSource` جديد فقط (رخيص) وغيّر `playbackRate` عشوائياً للتنويع:

```js
// في init()
this._crashBuf = this._makeNoiseBuffer(0.4);
// في playCrash()
const src = this.ctx.createBufferSource();
src.buffer = this._crashBuf;
src.playbackRate.value = 0.85 + Math.random() * 0.3;   // تنويع بلا تخصيص
```

**🟡 P2 — المركبة الأولى تُبنى قبل جاهزية دامج الهندسة**

`initThreeJS()` يستدعي `setupGeometryMerger()` **بلا `await`** (وهو صحيح، فهو تحسين
تدريجي)، لكن `initGame()` يبني المركبة مباشرة بعده بشكل متزامن:

```js
setupGeometryMerger();   // async، لسه ما رجع
...
vehicle = buildMeasuredVehicle(state.activeVehicle.id);   // mergeGeometriesFn لسه null
```

فأول مركبة (والمعروضة في المشهد الخلفي للقائمة) تبقى بـ ~250 mesh غير مدموجة. الحل
البسيط: بعد نجاح `setupGeometryMerger()` نادِ `rebuildVehicle(state.pendingVehicleId)`
مرة واحدة إن كنّا لا نزال في `phase === 'menu'`.

**🟡 P3 — الهدف والزينة لسه غير مدموجة (بعكس المركبات)**

`optimizeStaticGroup()` مطبّق على **بُناة المركبات الأربعة فقط**. أما `createGasStation()`
(~24 mesh خاص به + ٤ مركبات كاملة + نخيل) و`createCamp()` و`createOasis()` و`createTent()`
و`createPalmTree()` فتُضاف كما هي. المراجعة السابقة (H3) عالجت هذا **جزئياً** بإخفاء الهدف
خلف الضباب:

```js
World.goalMarker.visible = (World.goalMarker.position.z - vehicle.position.z) < level.fogFar + 20;
```

وهذا ممتاز لمعظم المرحلة، لكن في آخر ٦٠–١٠٠ متر — وهي **أهم لحظة في المرحلة** — يظهر
الهدف كاملاً دفعةً واحدة. تمرير `optimizeStaticGroup(group)` على مجموعات الهدف والخيام
والنخيل مكسب شبه مجاني (نفس الدالة، صفر كود جديد).

**🟡 P4 — مستوى الجودة التكيّفي لا يُحفظ بين الجلسات**

`updateAutoQuality()` ينزل درجة كل نافذة ٣ ثوانٍ من الإطارات المنخفضة، و`autoTier` متغير
محلي لا يُكتب في `SaveSystem`. جهاز ضعيف يحتاج الدرجة ٣ سيقضي **٩ ثوانٍ على الأقل من
التقطيع في بداية كل تشغيل** ليعيد اكتشاف نفس النتيجة. احفظ `settings.autoTierFloor` في
الحفظ وابدأ منه.

**⚠️ غير قابل للتقييم من الكود:** معدل الإطارات الفعلي، وكفاية سلّم الجودة الرباعي على
أجهزة متوسطة، وحجم اختناق بناء المرحلة (~55 ألف تقييم ارتفاع) رغم وجود `#loadingOverlay`
الذي يغطيه. يحتاج قياساً على جهاز حقيقي عبر `?debug=1` (اللوحة التشخيصية موجودة ومجهّزة).

## 2. تصميم اللعبة وتجربة اللاعب (وزن 40%) — **7.5/10**

### أ) الإحساس باللعب (Game Feel / Juice) — 8.0/10

**الآليات موجودة فعلاً في الكود، لا مجرد ادّعاء:**

| العنصر | الموضع في الكود |
|---|---|
| اهتزاز كاميرا عند الاصطدام | `state.shake` مع اضمحلال أسّي `Math.pow(0.02, delta)` |
| **Hit Stop** (تجميد المحاكاة ~70ms) | `state.hitStop` — والرسم يستمر، وهذا هو الصح |
| شظايا مجمّعة (pooled debris) | `spawnDebris()` + `updateDebris()` |
| اهتزاز الجهاز | `navigator.vibrate(120)` مع إعداد للإيقاف |
| قفزة السيارة عند الارتطام | `state.vehicleVelocityY = 6` |
| ميل الجسم مع التوجيه + انحدار الأرض | `terrainRoll` / `terrainPitch` بعيّنات أمامية/خلفية |
| كاميرا تتأخر عن السيارة | `state.cameraY += (…) * (1 - Math.exp(-6 * delta))` |
| دخان عند الصحة المنخفضة، آثار إطارات، غبار | `createSmokeParticles` / `updateTireTracks` / `updateDustParticles` |
| صوت محرك يتبع السرعة والتوجيه | `audio.updateEngine(speed, effSteering)` |

ومهم: `hitStop` و`shake` **معطّلان تحت `reduceMotionOn()`** — أي أن الـ juice محترم
لإعدادات الوصولية بدل أن يُفرض.

**🟠 U1 — نافذة الحصانة تحذف العقبات مجاناً**

`checkCollisions()` — تأمّل موضع القوس المغلق:

```js
if (now - state.lastCollisionTime > CONFIG.damage.invulnSeconds) {
    ...  // كل الضرر هنا
    state.lastCollisionTime = now;
}

vehicle.position.z -= 0.2;
removeInteractive(obstacle, World.obstacles, i, obstaclePool);   // ← خارج الشرط
return true;
```

خلال نصف ثانية الحصانة بعد أي ارتطام، السيارة **تمحو** كل عقبة تمر عليها بصفر ضرر —
وعلى سرعة ١٨ و/ث هذي ٩ أمتار من التدمير المجاني. النتيجة العملية: أي عنقود عقبات
متقارب (وهو بالضبط ما يولّده الوضع اللانهائي عند تصاعد الصعوبة) **يُبطَل بأول ارتطام
فيه**. والأسوأ أنه غير مفهوم للاعب: صخرة تختفي أمامه بلا سبب.

الحصانة نية سليمة، لكن معناها الصحيح هو **المرور من خلال** العقبة، لا إفناؤها:

```js
if (now - state.lastCollisionTime <= CONFIG.damage.invulnSeconds) continue;   // امرُر، ولا تحذف
```

### ب) التوازن ومنحنى الصعوبة — 7.5/10

**التحليل من الأرقام (وهذا الجزء *يُقاس* من الكود):**

الاستهلاك بالثانية لا بالمتر، فالمدى = `topSpeed / (burn × fuelEfficiency) × fuelCapacity`.
على المرحلة السادسة (١٣٠٠م، `fuelConsumption: 0.0212` أي 1.272%/ث عند السرعة العادية):

| المركبة | المدى بخزان كامل | الهامش على ١٣٠٠م | ضربات يتحملها |
|---|---|---|---|
| جيب قديم | ~1477 م | +13.6% | 3 |
| شاص | ~1415 م | +8.8% | 5 |
| بيك-أب | ~1397 م | +7.5% | 6 |
| شاحنة صغيرة | ~1321 م | **+1.6%** | 9 |

**المقايضة حقيقية ومختبَرة** — لا مركبة مهيمنة على المحورين، وهذا إنجاز توازن فعلي.
واقتصاد الخانق (throttle) مصمَّم بدقة رياضية: `burn = (1-1/e) + (1/e)·throttle^e` مع `e=6`،
فتكون ذروة المتر-لكل-وقود **عند السرعة العادية بالضبط** — الدوس يكلّف مدى، والزحف يهدر
وقوداً في التخميل. هذا يحوّل الخانق من زرّ مجاني إلى قرار.

**الملاحظات:**

**🟡 U2 — لا حدّ أدنى مضمون لعلب الوقود، والشاحنة على المرحلة ٦ رهينة الحظ**

`setupLevel()` يولّد العلب بتجارب برنولّي مستقلة:

```js
for (let z = 80; z < fuelEnd; z += 50) {
```

على المرحلة ٦: ٢٣ فرصة × 0.30 = ٧ علب متوقعة، لكن التوزيع ذيله مفتوح. احتمال ≤١ علبة
≈ **0.75%** — أي جولة من كل ١٣٠ تقريباً. مع هامش الشاحنة البالغ 1.6% فقط، وكل ارتطام
يخصم ٤ وقود (≈٥٠ متراً)، **الجولة تصير غير قابلة للفوز رياضياً قبل أن تبدأ**، واللاعب
يقضي ٩٠ ثانية ليكتشف ذلك. أضف ضماناً بسيطاً: بعد الحلقة، لو `World.fuelCans.length` أقل

**🟡 U3 — «تعزيز السرعة» ربح صافٍ بلا مقابل**

`boostMultiplier: 1.5` يضاعف السرعة، والاستهلاك **بالثانية** ولا يتأثر بالـ boost إطلاقاً.

التقاط قدرة معيّنة «فوز». اربط الـ boost بمعامل حرق (مثلاً ×1.35) فيصير قايضة: مسافة
أسرع مقابل مدى أقل.

**⚠️ غير قابل للتقييم من الكود:** منحنى الصعوبة المُحسّ عبر المراحل الست، وهل العاصفة
الرملية ممتعة أم محبِطة، وهل ٩–١٤ ثانية من العاصفة طويلة زيادة. يحتاج لعباً فعلياً.

## 3. المراجعة الأمنية ومكافحة الغش (وزن 20%) — **7.5/10**

### أ) نزاهة اللعب

**🔴 A1 — «التحدي اليومي» ليس واحداً للجميع فعلياً (حرج على مستوى نزاهة الوضع)**

هذا أخطر ما وجدته. `MODES` يعلن: *«بذرة يومية ثابتة للجميع»*، و`shareDailyScore()` يوفّر
زر مشاركة للنتيجة. لكن البذرة **تتسرب من أربعة مواضع مستقلة**:

**١) استهلاك البذرة مربوط بمعدل إطارات اللاعب** — وهذا وحده كافٍ لكسر الوضع.
في `gameLoop()`، الوضع اللانهائي (والتحدي اليومي يعمل كـ endless) يستهلك `rand()`
**ثلاث مرات على الأقل في كل إطار**:

```js
if (rand() < (0.04 + Math.min(0.08, state.distance / 30000)) * spawnScale) { … }
if (rand() < 0.02 * spawnScale) { … }
if (rand() < 0.012 * spawnScale) { … }
```

`spawnScale = delta * 60` يصحّح **الكثافة** بالثانية (وهذا صحيح ومقصود)، لكنه **لا يصحّح
عدد سحبات المولّد**. لاعب على شاشة 120Hz يستهلك ضِعف ما يستهلكه لاعب 60Hz من نفس التيار
المبذور. النتيجة: بعد الـ ٨٠٠ متر المُولَّدة مسبقاً، **التخطيطان يتباعدان تماماً**.
ولاعب على 144Hz أو جهاز يتقطّع فيه الإطار يحصل على مسار ثالث مختلف كلياً.

**٢) أحجام العقبات — أي صناديق التصادم — على `Math.random()` لا `rand()`**

`createObstacle()`:

```js
const rockSize = 0.7 + Math.random() * 1.0;
...
mesh.userData = { type: 'rock', radius: rockSize + 0.3, yOffset: rockSize * 0.3 };
```

`radius` **ليس زينة** — هو صندوق التصادم المستخدم في `checkCollisions()`. فحتى في الـ ٨٠٠
متر المبذورة، صخرة في نفس الموضع تكون بنصف قطر 1.0 عند لاعب و2.0 عند آخر. نفس المشكلة
في `holeSize` و`mesh.scale.y` و`mesh.rotation`.

**٣) توقيت العواصف الرملية عشوائي غير مبذور**

```js
state.endlessSandstormNext = 1200 + Math.random() * 800;                       // setupLevel
state.endlessSandstormNext = state.distance + 1200 + Math.random() * 1000;     // gameLoop
```

والعاصفة تخفض التوجيه إلى `0.7` وتقصّر الرؤية للنصف — أي أنها **أكبر مؤثر صعوبة في
الجولة**، وموضعها يختلف من لاعب لآخر.

**٤) إعادة التدوير من المخزن تتخطى سحبة النوع**

```js
function acquireObstacle(z, forcedX) {
    const o = obstaclePool.pop();
    if (o) { reposition(o, z, forcedX); return o; }   // ما استهلك rand() للنوع
    return createObstacle(z, forcedX);                 // بينما هذا يستهلكها
}
```

فتسلسل «صخرة أم حفرة» ينفصل عن التيار المبذور بمجرد أن تبدأ إعادة التدوير.

**وأخيراً**، حتى لو أُصلح كل ما سبق: `beginRun()` يثبّت `pendingLevel = 0` للتحدي اليومي
لكن **يترك اختيار المركبة حراً**، والنتيجة مسافة. الجيب (سرعة ٢١، أطول مدى) يتفوّق
بنيوياً في وضعٍ درجتُه هي المسافة. فنتيجتان مُشاركتان لنفس اليوم **غير قابلتين للمقارنة
أصلاً**.

**الإصلاح المقترح (مرتّب):**
1. مرّر كل `Math.random()` مؤثّرة على اللعب داخل `createObstacle`/`createCamel`/العواصف
   إلى `rand()`.
2. افصل استهلاك البذرة عن الإطار: بدل السحب لكل إطار، ولّد التوليد على **شبكة مسافة
   ثابتة** (مثلاً كل ١٨ متراً كما في التوليد المسبق) بحيث تعتمد سحبات المولّد على `z`
   لا على عدد الإطارات.
3. اجعل `acquireObstacle()` تستهلك نفس عدد السحبات في المسارين، أو استخدم مولّداً
   منفصلاً للتخطيط مفهرساً بالمسافة.
4. ثبّت المركبة في التحدي اليومي (مثلاً «شاص» دائماً)، أو ضمّن معرّف المركبة في نص
   المشاركة.
5. أضف اختباراً: شغّل نفس البذرة بـ `delta` مختلفَين وتحقّق أن تسلسل `(z, x, type, radius)`
   متطابق. لديك بنية اختبار ممتازة أصلاً — هذا الاختبار يقفل الباب نهائياً.

**🟡 A2 — ملف الحفظ نص صريح — وهذا مقبول هنا**

`SAVE_KEY = 'desertSurvival3D.v1'` في `localStorage` بلا توقيع. **لست أعدّه ثغرة**:
اللعبة فردية أوفلاين بلا خادم ولا لوحة نتائج، والغش فيها يضر الغاشّ وحده. تشفيرها سيكون
هندسة أمنية زائدة (security theater). أُبقيها ملاحظة فقط لأن `shareDailyScore()` يخرج
نتيجة من الجهاز — والنص المشارَك **ادّعاء غير قابل للتحقق** بطبيعته. طالما لا يوجد خادم،
هذا حدّ التصميم المقبول، ويكفي ألا يُقدَّم كـ«لوحة نتائج».

**🟡 A3 — استئناف نقطة التفتيش يظل يسجّل أفضل زمن**

`restoreCheckpoint()` يضبط `damageTakenThisLevel = true` (فيُفقد نجم «بلا خدش» — صح)،
ويبقي `checkpointSnapshot` قابلاً لإعادة الاستخدام إلى الأبد. لكن `completeLevel()` يسجّل
`bestTimes[lvl]` ونجمة الزمن القياسي بلا تمييز. عملياً: تقدر تعيد النصف الثاني عشرات
المرات من نفس اللقطة وتُبقي زمن النصف الأول المثالي. الأنظف: أعلِم اللقطة براية
`resumed: true` واستبعد الجولات المستأنَفة من `bestTimes` ومن نجمة الزمن.

**🟡 A4 — جولات التحدي اليومي تلوّث سجل الوضع اللانهائي**

`gameOver()`:

```js
if (state.mode === 'endless') {          // التحدي اليومي يدخل هنا لأنه mode === 'endless'
    if (dist > SaveSystem.data.endless.bestDistance) SaveSystem.data.endless.bestDistance = dist;
    SaveSystem.data.endless.runsCompleted++;
    ...
    if (dist >= 1000) unlockAchievement('endless_1k');

```

وضع مبذور ومضبوط يكتب في رقم الوضع الحرّ ويفتح إنجازاته. فصل بسيط: `if (!state.daily)`
حول كتلة `endless`.

### ب) الأمن التقليدي

**ما هو سليم — وأقولها لأنه غير شائع:**

- **صفر سطح XSS.** لا يوجد أي حقل إدخال نصي في اللعبة (لا اسم لاعب، لا دردشة). كل
  `innerHTML` يُبنى من ثوابت `CONFIG`/`VEHICLES`/`ACHIEVEMENTS` المكتوبة في الملف نفسه.
  كل نص متغيّر يمرّ عبر `textContent`. فحصتُ كل موضع.
- **صفر أسرار.** لا مفاتيح API، لا رموز، لا نقاط نهاية.
- **CSP فعلي** في `<meta>` مع `object-src 'none'` و`base-uri 'none'` و`form-action 'none'`
  وحصر `connect-src` بالأصل + CDN واحد مثبّت. `'unsafe-inline'` مفروض بقيد الملف الواحد
  ومُبرَّر في تعليق.
- **Service Worker محكم**: يرفض تخزين استجابات `opaque` (كان يخزّن صفحات 404 من الـ CDN
  كأنها الوحدة، فتنكسر اللعبة أوفلاين للأبد)، ويحدّ تحديث `index.html` على مسارات
  قشرة التطبيق فقط.

**🟠 A5 — تثبيت SRI عبر `integrity` في import map غير مدعوم في Safari/Firefox**

```html
<script type="importmap">
{ "imports": { … }, "integrity": { "https://cdn.jsdelivr.net/…/three.module.js": "sha384-…" } }
</script>
```

حقل `integrity` داخل import maps ميزة حديثة نسبياً (Chromium أساساً). في Safari وFirefox
يُتجاهَل الحقل بصمت، فتُحمَّل وحدات Three.js من الـ CDN **بلا أي تحقق من التكامل**.
التعليق في الملف يقول *«SRI-pinned in the importmap below»* بصيغة قاطعة تُخفي هذا الحدّ.

المعالجة (بترتيب القوة):
1. **استضف `three.module.js` محلياً** — يلغي الاعتماد على CDN تماماً، ويناسب مشروعاً
   يُشحن أصلاً كـ PWA أوفلاين ويُسبِق تخزين الملف في الـ Service Worker على أي حال. هذا
   الخيار الصحيح استراتيجياً.
2. أو على الأقل عدّل التعليق ليقول إن التثبيت يسري على المتصفحات الداعمة فقط.

**🟡 A6 — Three.js r0.160.0 متأخر ~سنتين**

لجمهور يشمل قاصرين. `navigator.share` يمرّر نصاً مبنياً محلياً فقط. لا ملاحظة.

**تعليق على الدرجة:** ٧.٧ درجة **مرتفعة** بمقاييسي، وهي أعلى مما تحصل عليه أغلب ألعاب
الويب المكتوبة بملف واحد. الهندسة هنا في مستوى مشروع محترف: delta-time صحيح رياضياً،
مشتقة تحليلية للتضاريس **مغطاة باختبار مقارنة مع المشتقة العددية**، آلة حالة واحدة،

شيئان محدَّدان لا أكثر: **كسر بذرة التحدي اليومي** (وضع كامل لا يفي بوعده المعلن)،

## 6. سؤال الحكم النهائي

### «لو لعبت هذي اللعبة ١٠ دقائق، هل بأكمل؟»

**نعم، بكمّل — وغالباً بتجاوز العشر دقائق.** وهذي إجابة كلاعب لا كمراجع كود.

الدقيقة الأولى هي ثقل المشروع: مودال ١١ نقطة قبل ما أشوف صخرة واحدة، فبأغلقه بلا قراءة
(كل اللاعبين يسوّون كذا). لكن أول ما أنطلق، اللعبة **تشتغل صح**: السيارة تميل مع الكثبان،
الكاميرا تتأخر عنها فأحسّ بالوزن، أول اصطدام يعطيني تجميداً قصيراً واهتزازاً وشظايا —
وهذا يفرّق كثيراً بين لعبة «تشتغل» ولعبة «تُحَسّ».

**ما يخلّيني أكمل تحديداً:** الوقود ليس عدّاداً تزييناً — هو **القيد الحقيقي**. الأرقام
تقول إن جولة نظيفة تستهلك أغلب الخزان، فكل علبة تفوّتها قرار له ثمن، وقرار الدوس/الفرملة
له اقتصاد فعلي بذروة عند السرعة العادية. هذا يحوّل «امسك الجاز للأمام» إلى لعبة إدارة
موارد صغيرة تحت الضغط. وأربع مركبات بمقايضة **مثبتة باختبار** (لا واحدة مهيمنة على
المحورين) تعطيني سبباً حقيقياً لإعادة نفس المرحلة بخيار مختلف.

**وش يوقفني؟** الموت. أموت على ٩٠٠ متر، وأجلس **٣.٥ ثانية** أتفرّج على كاميرا تلفّ حول
حطامي بلا أي مفتاح يخطّيها، ثم أنقر، ثم أنتظر بناء المرحلة. مرة أو مرتين ماشي. المرة
الخامسة أقفل التبويب. في لعبة أركيد كل شيء فيها مبني على «مرة ثانية»، هذي أغلى ٣.٥
ثانية في المشروع كله — وهي اللحظة الوحيدة اللي حسّيت فيها إن اللعبة تعاقبني بدل ما
تحفّزني.

### أقوى نقطة

**الانضباط الهندسي المُثبَت، لا المُدّعى.** المشروع ما يكتفي بأن يشتغل — بل يقفل الأبواب
خلفه: `getTerrainSlope` مشتقة تحليلية **مغطاة باختبار يقارنها بالمشتقة العددية على شبكة
كثيفة**، وحارس اختباري يمنع رجوع `Math.random()` داخل حلقة رؤوس الصخرة، واختبار توازن
يمنع أي مركبة من الهيمنة على المحورين، واختبارات تُشغّل **الكود المشحون نفسه** المستخرَج
من `index.html` لا نسخة موازية تتعفّن. كل خطأ أُصلح خلّف وراءه اختباراً يمنع رجوعه. هذا
مستوى نضج نادر جداً في لعبة ويب بملف واحد، وهو ما رفع الدرجة الهندسية.

### أضعف نقطة تحتاج إصلاحاً فورياً

**«التحدي اليومي» يَعِد بشيء لا يوفّره.** الوضع مكتوب في القائمة كـ«بذرة يومية ثابتة
للجميع»، ومعه زر مشاركة نتيجة. لكن أربعة تسريبات مستقلة تكسر البذرة، وأخطرها أن استهلاك
المولّد مربوط بعدد الإطارات: لاعب على 120Hz يستهلك ضعف السحبات، فيحصل على مسار مختلف
كلياً بعد أول ٨٠٠ متر. وحتى الصخور المشتركة تختلف **صناديق تصادمها** لأن `rockSize` على
`Math.random()`. النتيجة أن نتيجتين مُشاركتين لنفس اليوم لا تعنيان شيئاً — وهذا أسوأ من
عدم وجود الوضع، لأنه يبيع للّاعب إحساساً بالمنافسة العادلة وهو غير موجود.

الخبر الجيد: البنية الصحيحة موجودة بالكامل (`mulberry32` + `hashStr` + `todaySeedString`
بالـ UTC + `_spawnRng` + الاختبارات). المطلوب توصيل الأسلاك الأربعة الباقية وإضافة اختبار
واحد يشغّل نفس البذرة بـ `delta` مختلفَين ويقارن التسلسل. يوم عمل واحد، ووضع كامل يتحوّل
من وعد مكسور إلى أقوى سبب للعودة يومياً.
